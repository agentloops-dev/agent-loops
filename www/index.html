From idea to production, and back.

Agent Loops runs a team of coding agents for you. They plan the work with you, build it, get it through your CI, merge it and ship it. You stay in the loop for the decisions that need a person, from your Mac, your phone, a browser or the terminal, and the agents get on with the rest.

The whole lifecycle, not only the code

Writing the code is only one part of delivering a change. Agent Loops covers the whole journey, from the first idea to the change running in production. Agents do each step, and they come to you when a decision needs a person.

1

Idea to feature

  • Tell a product owner agent your idea, by typing or out loud. It talks it through with you, then files the issues.
  • The feature lands in your tracker as ordered issues, each with a size and a priority.
  • You agree the plan before any agent starts work.
2

Feature to merged PRs

  • A lead agent starts an agent for each issue, each in its own worktree, on whichever of your machines has room.
  • Your CI decides what is good enough. Agents run it, read each failure and fix it, so you do not have to.
  • A change that adds a new screen waits for you to approve it.
3

Deploy, watch, roll back

  • See every deploy in every environment on one page.
  • When something breaks in production, the error goes back into work as a new issue.
  • A deploy that needs an approval comes to you, wherever you are.
  • Agents will watch a canary and roll it back when it goes wrong. coming

A feature builds and deploys itself

Here is one feature from idea to production. You say the idea out loud. A product owner agent turns it into five issues, and a lead agent shares them out across three machines. When every pull request has merged, the feature deploys and its monitoring watches it in production. Your only job is to approve the one new screen.

Work management, in your tracker

Your issues and pull requests stay where they are, in GitHub, GitLab, Bitbucket, Jira, Linear or Azure Boards. Agent Loops reads them, puts them in one order, and has agents work through them. There is no second board to keep up to date.

  • One queue. Next puts the work that is ready in one order: priority first, then the milestone's date, then age.
  • Each feature has a lead. A lead agent starts an agent for each issue as soon as nothing blocks it.
  • Know what it will take. Estimates come from your own finished work, and a forecast gives the dates a feature is likely to land between.
  • See who is on it. Issues, pull requests, releases, deploys and a timeline, and each issue and pull request says when an agent is working on it or needs you.

Agents that start on events, and wait for them

A workflow is a Markdown file in your repository. An event, such as a red build, a new issue, a review or a message, starts an agent on it. An agent that must wait, for CI, a review or another agent, ends its turn and wakes when the event comes. It costs nothing while it waits.

Events come from GitHub, GitLab, Jira, Linear, Sentry, Slack, mail, your machines and your other agents, and on a schedule. Agents take turns on a simulator, a browser or the CI queue with leases.

Put agents on the work nobody wants at 2 a.m.

Each use case is a workflow: an event starts an agent, the agent does the work, and you read what happened in the morning. Here are two of them, from the first alarm to the fix.

Fix a broken build

Main goes red, and an agent finds the cause and fixes forward.

Fix failed checks

A pull request's CI fails, and its agent reads the log and pushes a fix.

Answer review comments

A reviewer comments, and the agent changes the code and replies.

Work an issue

An issue gets the label agent in GitHub, GitLab, Jira or Linear, and an agent takes it.

Errors become bugs

Sentry sees a new error, or an old one comes back, and it becomes a bug with its stack.

Make CI faster

CI's median time goes over 15 minutes, and an agent makes one change that makes it faster.

Keep performance budgets

Each night, an agent measures the app against its budgets and files an issue for a time that is over.

Security alerts

A critical or high Dependabot alert becomes a high-priority bug, and the bug lane fixes it.

Flaky tests

A test fails that the change does not touch. The agent runs it 20 times, then fixes the bug or puts the test aside with an issue.

Crash reports

The app crashed, and an agent files an issue, or comments on the issue that has it already.

Release

You say go, and an agent writes the notes, runs the checks, tags the version and sends the store build.

Daily checks

Every few hours, an agent looks for a red build, a stuck pull request or a missed workflow, and tells you.

Agents use the computer, as you do

Some work has no API. So an agent can drive a browser, the apps on your Mac and the iOS simulator, to test what it built or to do the step that only a screen can do. You can watch it live, from any device.

Its own browser

It has a browser and sign-ins of its own. It fills in a password without seeing it, and it can use a passkey. When a page asks for a person, it hands that one step to you.

The apps on your Mac

It uses the screen, mouse and keyboard, when you turn this on. One agent has the screen at a time. Move your mouse and it stops, until you let it go on.

The iOS simulator

It runs the app it built, tries it out, and puts the screenshots on the pull request. The simulator shows beside the chat, and agents take turns with a lease.

Lineage: know what really went into your delivery

Agent Loops links every issue, agent session, pull request, release, deploy and error as the work happens. So you can ask the questions a status meeting cannot answer.

Scale delivery the way you scale production

Your development system is a fleet, as production is. Add a machine, and more work runs at once. Agents can make, start and stop cloud machines, and a new one is made only when you say yes.

  • Any machine. Your Mac, your own Linux servers, and cloud machines on DigitalOcean, AWS, Google Cloud, GitHub Codespaces or Coder.
  • Capacity. Each machine says how busy it is. When one is near full, heavy work and new agents wait in line.
  • Labels. A workflow says which machines it runs on, such as linux, macos or one cloud provider.
  • Priorities. When places are short, the urgent work goes to the front of the line.
  • Work that moves. Send an agent to another machine with its unpushed work, and bring the branch back.
  • Costs you control. A cloud machine starts when it is used and stops when it is idle. Policies limit how many agents run, and spending limits stop what they cost.

Reports: see how delivery goes

The figures come from the records your agents and your CI already make. There is no survey to fill in and no extra tool to run.

There are pages for time, runtimes, adoption, workflows and estimates too, on the web. Save a view, export it as CSV, read it from your own tools with the read API, or send the figures to an OpenTelemetry collector.
