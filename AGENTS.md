# AGENTS.md

## Context routing

- **For the project's purpose and setup:** READ `README.md`.
- **For architecture, terminology and decisions:** CONSULT `docs/`.
- **For hosting, sign-in, trust and customer data:** FOLLOW the principles in `docs/explanation/direction.md` (#3403). A spec, plan or issue agrees with them, or says which one it leaves out and why.
- **For a task a skill covers:** USE the skill in `.agents/skills/`.
- **When a task calls for a specialist perspective:** ADOPT a persona from `.agents/personas/`.

## Libraries before our own code

- Before writing a parser, protocol, client, format or algorithm, look for a library. Use it when one fits.
- A fit library has a permissive licence (MIT, Apache-2.0, BSD or ISC; no GPL/AGPL in the apps), was released or updated in the last 12 months, has users, and has a pinned version that Dependabot watches (`Package.resolved`, `go.sum` or an exact `package.json` version).
- Prefer the platform library (Foundation, Go standard library or the browser), then the protocol or service's official SDK, then a widely used community library.
- Write our own code only when no fit library exists or the library costs too much where it runs. State the reason in the PR. For a library added by a PR, state its purpose, licence and size.

## Durable data

- Store data in the project itself when possible.
- When important long-term data cannot safely live in the project, store it on disk in `~/.agents` when safe. Do not rely on an agent's memory for data that can safely be stored there.

## Keeping the three clients in step

- **Three clients draw the same product:** the Mac window (`App/`), the Remote on iPhone and iPad (`Remote/`), and the web page (`Web/`). `Shared/UI` is drawn by both the window and the Remote.
- **Each feature has a tier (#2796):** the Tier cell of its row in the parity table, below. The Mac window and the web page are full clients. The tiers trim only the Remote, with one exception: a Web + Mac link feature is not drawn on the Mac.
  - **Core:** all three clients (the session list, chat, question cards, the prompt bar, approvals, notices, the Brief, and the session and folder work the Remote keeps). The parity table lists it all.
  - **Mac + web:** the Mac window and the web page. The Remote gets no parity issue and does not have the feature: #2798 removes it, with no line in its place (Alex, 2026-10-29).
  - **Web + Mac link (#4937):** the web page has the feature. The Mac window shows one link to it, where a person looks for it, and draws nothing more. The Remote gets nothing, as for Mac + web. This tier is for features that people use rarely and that cost much to build natively (Reports, the Console's admin pages; epic #4936). Each link:
    - shows only when the web page is served and this Mac can open it (the rule of **Edit in Console**). A Mac with no web page has no link and no feature;
    - opens the right place (the section, page, scope and range, as `#/reports/…`), not the Overview;
    - signs the browser in as **Open in Browser** does: with the control plane on this Mac, it pairs the default browser in the same step the first time; with the control plane somewhere else, the web page's own sign-in, which keeps the address through the sign-in. The link carries no code or token.
  - **Mac only, Web only, Remote only (#4759; was One client):** one client only, by design, no follow-up. **Web only** is the web page with no link from the Mac: by #3224, reports, figures about other people and the Console's admin pages that the Mac has no part of, and the web's own frame and ways in. The parity table's Web only list names them.
  - A new report, team or admin feature is Web only (#3224), unless Alex chooses Web + Mac link. Any other new feature that is on none of the parity table's lists is Mac + web.
- **A feature has a role first, and its tier follows (#5290, epic #5288).** The role is who uses it: Engineer (agent work), Engineer (set-up), Lead, Admin or Report reader; it is the Role cell after Tier in the parity table, and a Maturity cell (`ga`, or a level with its capabilities) follows it, checked against `Packages/Wire/maturity.json` (#6580). The rule (`parity.md`, "Roles"): Engineer (agent work) is Core (Desk, Hand, Web); Engineer (set-up) is Mac + web (Desk, Web); Lead and Report reader are Web, with a link from the Desk, and no Hand (Velocity and Timeline stay Core); Admin is Web only, or Web + Mac link where an engineer looks for it. A new feature gets a role; its tier follows. `scripts/parity-counts.py` fails on a row whose tier its role does not give.
- **A change to any client's UI** (`App/Sources`, `Remote/Sources`, `Shared/UI` or `Web/src`) says, in its commit, what **each of the other two** does about it, one line each:
  - the same change in this branch: `remote: same`;
  - a parity issue filed: `web: #NNN`. For an MVP, `remote: #NNN` and `web: #NNN` can name children of its port epic ("Plans", #7037);
  - left out on purpose: `mac: by design (no swipe on Mac)`;
  - not on the Remote because of its tier: `remote: tier mac+web`, or `remote: tier web+link`; not on a client because it is one client's only: `mac: tier web only`, `remote: tier web only`, or `web: tier mac only`;
  - a web change to a Web + Mac link feature: `mac: tier web+link` when the Mac's link still goes to the right place, else `mac: same` (the link changes in this branch) or `mac: #NNN`.
- **For example,** a Mac sidebar change ends with `remote: #226` and `web: same`; a new Settings ▸ People control ends with `remote: tier mac+web` and `web: same`; a web-only fix ends with `mac: same, remote: same` when both already do it. A change to docs only says `mac: docs only, remote: docs only, web: docs only`.
- **A page with cached data says "Last update <time ago>" (Alex, 2026-11-12, #5139).** Every page or pane that shows data from an earlier read (the local copy, a read while its source does not answer, a read when it opens, a poll of 30 s or more) shows the time of that read, with the same words on all three clients. A new page follows it too. The rule is in `docs/reference/design-system.md`, "How fresh the data is".
- **The table of where each client stands** is `specs/071-web-remote/walks/parity.md`, a page that `scripts/docs-parts.py` makes from `docs-parts/parity/` (edit a part there and run it, #5386), a file per screen under `walks/parity/` (Mac / Remote / web, a row per feature; #2020). `scripts/parity-counts.py` counts the verdicts and the tiers. A parity line that changes a row updates it in the same branch.

## Verifying a lane's work

- **A lane verifies only what it touched, with Nx (#5628, #5631, epic #5627):** `scripts/nx.sh affected -t gen build vet lint test`, under the "build" lease. It runs only the tasks of the projects that the branch changes since `origin/main`, and gets a task that ran at the same inputs in any worktree from the cache in `~/.nx`: `go:build`, `go:vet`, `go:test` (with `-race`), `go:lint`, `web:build`, `web:lint`, `web:test`, `repo-lint:lint`, `swift-lint:lint`, `wire:gen`, `design:gen`, `mac:build` (`AgentsHost`, Agent Loops, the one Mac app), `remote:build` (the Remote), `agentskit:test` (its unit, control and integration targets), `agentskit-repo:test` (the suites that read files outside the package) and `codetext:test`. The Swift tasks run through `scripts/build-cache.sh`, so Xcode's compilation cache and SwiftPM's stay below Nx. It is what CI's three jobs run (#5645), side by side after a one-minute `changes` job that says which of them a change needs (#5677): `go` on Linux, `apps` and `test` on macOS (`test` is the gate over three macOS jobs side by side: `test-swift`, the packages; `swift-lint`, SwiftLint (#6336; no Periphery since #6526); and `test-go`, the Go tasks on a Mac; #5755); there is no other full run. `--exclude='tag:xcode'` leaves out the Swift tasks, and `scripts/nx.sh run agentskit:test-unit` runs one task. `scripts/nx.sh` installs the pinned pnpm and packages first (`scripts/pnpm.sh install --frozen-lockfile`). It streams each task's output as the task runs (`NX_DEFAULT_OUTPUT_STYLE=stream`, #5887), and CI passes `--output-style=stream`: a hung or slow task shows its last lines, not nothing. Without it, Nx 24 prints only a log path for an agent (`summary`), and `static` prints a task's output only when it ends. The Go tasks run the Mac's own Go, not a container (#4709): a failure only Linux has still shows only in CI's `go` job.
- **CI on the remote runners is the only gate (Alex, 2026-11-20, #6438; replaces the attestations of epic #5581).** A lane runs only what it needs to show that its own change works (one task, or `scripts/nx.sh affected` for what it touched), then pushes. It does not run the whole suite again before a push, and posts nothing for CI to skip: CI's `go`, `apps` and `test` jobs run every affected task on each pull request.
- **Each task's inputs are in its project's `project.json`.** A task that reads a file outside its project names it there, and a task that reads generated files names the generator's sources, or a cache hit is a false pass. A folder that a task reads but no project owns (`Host/`, `Shared/`, `specs/`, `scripts/`, …) is a project with no targets (tag `inputs-only`), named in the task's project's `implicitDependencies`, so `affected` sees a change to it. Each tool's version is in a file the hashes read: `Go/go.mod`, `Web/.node-version` and `.xcode-version` (the Xcode CI builds with). Never connect Nx Cloud, add an Nx plugin or install without `--frozen-lockfile`.
- **Lint with Nx, one target per language; every linter fails on a finding** (#1224, #5645, #5672): `go:lint` (golangci-lint, every rule in `Go/.golangci.yml`, govulncheck, and deadcode on all Go code with no baseline, #6334), `web:lint` (tsc, `test/lint.mjs`, the licence list, Biome, and Knip on all web code with no baseline, #6337), `repo-lint:lint` (shellcheck, `zsh -n`, our text checks and jscpd) in CI's `go` job, and `swift-lint:lint` (SwiftLint; Periphery was removed, #6526) in its `swift-lint` job. `scripts/nx.sh affected -t lint` runs those of what the branch changes; `scripts/lint.sh <linter>` runs one, and is what each target runs. golangci-lint, SwiftLint and jscpd fail only on a finding that is not in their baseline (`Go/.golangci-baseline.txt`, `.swiftlint-baseline.json`, `.jscpd-baseline.txt`): fix an old finding, then run `scripts/lint.sh --baseline` to drop it; never add a new one to a baseline. A finding that is right on purpose gets a suppression on its line with the reason (`biome-ignore …: why`). `docs/reference/linters.md` says what each fails on. There is no Python linter. On the Mac each runs on the host, never in a container (#4709): the pinned binaries go to `~/Library/Caches/Agents-build/lint-tools/` the first time, and Go comes from `brew install go`. With no linter named, `scripts/lint.sh` on a Mac runs only the linters for the files the branch changes (#4710), and says which it skipped; `--all` runs every one. `scripts/lint.sh --fix` runs the fix modes.
- **Build through `scripts/build-cache.sh`** (`… xcodebuild …`, `… swift test …`): one package and compilation cache in `~/Library/Caches/Agents-build/` for every worktree, so a fresh worktree is not a cold build. Deleting a worktree's own `build/` and `.build` when done is still the rule; the cache stays. Its `swift test` sets `AGENTS_QUARANTINE=1`, so tests marked `.flakyUnderLoad` skip as on CI; `AGENTS_QUARANTINE=0` runs them.
- **Before any xcodebuild, swift build, swift test, scripts/web.sh build or ship.sh, lease the resource "build" with lease_resource (minutes sized to the job, at most 60), and release it with release_resource the moment the command ends.** Never hold it while reading, editing or waiting on the screen.
- **Close every scratch app you ran** (run-app, the walk simulator, headless Chrome) with the run-app skill's "When you are done" steps before you commit or end. A scratch app left running is a bug in the lane.
- **A walk does not hold a place:** a lane that needs one commits, hands the walk on, and ends.

## Work by epic, release from main (#1340, #3465, #3760)

- **Milestones are themes, not versions (Alex, 2026-11-06, #3760).** A milestone is named by its theme only (`Projects`, `Channels`, `Runtime assessments`), and its GitHub due date gives the order; the due date is only for the order, and the milestone's description says so, with its goal and its place (#1340). `1.0 Public release` is the one milestone that keeps a version. **Why:** since #3465 a version holds more than its milestone, and a new order meant new numbers for every milestone.

- **Work goes by epic (Alex, 2026-11-04, #3465).** Each epic has a lead (#3265): a session with the Lead persona (`.agents/personas/lead.md`), started with Start lead in Work or by Alex. Several epics run at once, under the lane and open-PR limits. When there are more epics than places, they go in the one order of `forge/next` (#5689, #5692): not on hold first, then priority (`high`, `medium`, none, `low`), then the milestone's due date (the earliest first, none last), then the oldest. `forge/next` with `level: epic` gives the epics in it; with `epic`, an epic's ready children; Work ▸ Next shows the same. An issue that is in no epic goes by the same order. Nobody works out another order from prose. An issue with no milestone is the backlog, except bugs and enhancements that are no epic's sub-issue, which have standing epics of their own (below): the backlog is the issues with no milestone that neither standing epic takes.
- **A milestone is a set of epics and issues, not a gate (#3465; replaces #2309).** Work from a later milestone can run and merge before an earlier milestone ships. No issue is `parked` for its milestone.
- **A filed issue gets a milestone** only when it serves that milestone's goal (#1340).
- **Bugs have no milestone (Alex, 2026-11-01, #3212).** A bug is filed with no milestone, whatever its theme. The **bug lane** is a standing epic, #4207: its lead works the open bugs with no milestone always, in the background, as ordinary work, `priority:high` first, under the same open-PR limits. The exception is a bug that blocks a milestone's goal; it keeps that milestone, as a competitor gap that serves a goal does. **Why:** a patch milestone held features off `main`, so nobody could test them there, and that slowed the whole cycle.
- **Polish and competitor gaps have no milestone.** Issues labelled `polish` or `competitor` stay out of milestones. The exception is a competitor gap that serves a milestone's goal; it keeps that milestone. They are enhancements, so the standing epic for enhancements with no parent, #4208, works them with every other enhancement that has no milestone and no parent (#4335), alongside the milestone lanes, highest priority first, under the same open-PR limits. They are for no milestone, so they can merge before a release ships (#1570).
- **Standing epics are the standing lanes (#3659, #3664).** A standing epic has the labels `epic` and `standing`, and its plan is a query in a `standing` block in its body, not sub-issues (`specs/3659-standing-epics/spec.md`). It never closes. This folder has two: the bug lane, #4207 (`labels: bug`, `milestone: none`), and enhancements with no parent, #4208 (`labels: enhancement`, `milestone: none`, `parent: none`; #4335). Each one has a lead, as any epic does; the lead runs the block's `lanes:` lanes at once (1 when it says none) and takes the query's issues in the order of `forge/next` (#5692). When places run short, a standing epic's lane is paused before a milestone epic's lane (never a UI lane before a non-UI one). Their blocks are the Product Owner's and Alex's.
- **Spare places go in this order** (#1604, #3212, #3465), always within the open-PR limits: the milestones' epics and the bug lane's epic (#4207) together; then the epic for enhancements with no parent (#4208, #1570, #4335); then backlog issues with no milestone. Within each, the order is `forge/next`'s.
- **UI changes go early (Alex, 2026-10-22, #2337).** **UI changes** are anything that changes what a client shows (`App/Sources`, `Remote/Sources`, `Shared/UI`, `Web/src`), in the milestones, the bug lane and the backlog alike. They go early by their priority: a UI change is filed `priority:medium` ("Set a priority when you file", below), so `forge/next` puts it above the issues with no priority (#5692). For lanes that already run, places still favour UI: when places run short, pause a non-UI lane, never a UI one. **Why:** a person must review each UI change, so it must get to `main` and TestFlight early. A UI enhancement gets its place early too; one that adds a new screen, control or layout merges only after Alex approves it ("A UI enhancement waits for Alex", below, #2811, #3474).
- **Core usability goes first (Alex, 2026-10-27, #2800).** When milestones are put in order, a milestone that improves the app's core usability goes before the others. Core usability is what a person does in the app every day: start a session, choose a runtime, read and answer agents. A milestone that is useful to one person is core usability; a milestone that reaches people who are not the user (Hosted, Channels) is not. **Why:** this is why Auto runtime and voice mode and Lineage and value went before Hosted and Channels. The order is in #1340 and in each milestone's description.
- **No patch milestones (Alex, 2026-11-01, #3212; replaces #2801 and #2779).** A release makes no `x.y.1 Bug fixes` milestone, and nothing is held for a patch: enhancements merge as usual (a UI enhancement still waits for Alex's approval, #2811). **A release ships what is on `main`:** when a bug fix must reach people sooner, the next release takes it. Every release is a minor (x.y.0).
- **The release reviews are paused until 1.0 (Alex, 2026-11-01, #3215).** The release runs no security, performance, HADR, dead-code or usability review: before 1.0 the product changes too fast for them to pay back what they cost. The dead-code review runs on its own schedule instead (Tuesday, Thursday and Saturday; Alex, 2026-11-06, #3715). It still runs the runtime check, the competitor check and the feature matrix, and files a `priority:high` bug for each critical or high Dependabot alert. #3216 brings the reviews back at 1.0, at PR time. The other four reviews' skills and workflows stay, turned off.
- **Releases go out from `main` on their own schedule (#3760; replaces the #3465 gate).** A release starts when something merged since the last tag, at most one a day, and is the next minor. No milestone blocks it, except that the release that takes 1.0.0 waits until `1.0 Public release` has no open item.
- **A milestone never closes with open issues (Alex, 2026-10-22, #2455).** The release skill closes only a milestone whose items are all closed. **Why:** nothing schedules an issue left in a closed milestone.
- **One release a day (Alex, 2026-10-22, #2462).** At most one tag per calendar day in America/Los_Angeles; the release skill's readiness check and gate wait for the next day.
- **A milestone is done when its last item closes** (#3760), not when a release ships. It reaches people in the next release, whose notes name it under `## Milestones finished`; the release skill then closes it.

## Plans: features, epics, stories, tasks and spikes (#3265)

- **Work has one hierarchy** (`specs/3265-work-plans/spec.md`). The level is a label, used in addition to the type label (`bug`, `enhancement`), which the rules above and below still use:

  | Level | On the forge | Worked by |
  |---|---|---|
  | **Feature** | the label `feature:<name>`, a product theme; spans epics and milestones | nobody directly |
  | **Epic** | a parent issue, label `epic`; its children are its plan | one lead |
  | **Story** | a sub-issue, label `story`: a person can see or use it (a client or a workflow changes) | a lane: one PR or one stack |
  | **Task** | a sub-issue, label `task`: it changes no client (daemon, wire, tooling, docs) | a lane: one PR |
  | **Spike** | a sub-issue, label `spike`: a question with a time limit; it ends in a decision in the issue or a spec, not product code | a lane, or the lead |
  | **Bug** | label `bug`, as before; it can also be an epic's child | the bug lane, or the epic's lead |

- **A feature is a label, not an issue,** because a feature outlasts its epics. An epic belongs to one feature, and its children get the same `feature:` label. Only open issues get `epic` and `feature:`; closed epics keep their labels.
- **`feature:<name>`** is the product theme that the Product Owner sets when it files the issue. There are no `area:<name>` labels any more (Alex, 2026-11-10): the areas of #873 locked a set of paths to one lane at a time, and that lock held work up more than it saved rebases.
- **Every issue gets a size when it is filed (Alex, 2026-11-10, #4532).** Every agent that files an issue (the Product Owner, a lead, the bug lane, a review or check) sets one `size:` label, `size:XS` to `size:XL`, from the points rubric in `.agents/personas/product-owner.md`. An epic gets none. Never change a size after filing: the backtest in `specs/3557-estimates/spec.md` compares it with the actual cost.
- **Set a priority when you file (#5692, epic #5687).** Every agent that files an issue (the Product Owner, a lead, the bug lane, a review or check) sets its priority, because `forge/next` and a session's priority (#5847) follow it, so urgent work skips the queue:
  - `priority:high`: a blocker (`main` broken, a release blocker, a critical or high Dependabot alert), or Alex says so;
  - `priority:medium`: a UI change, or core usability (#2800);
  - no priority label: the rest;
  - `priority:low`: nice to have.

  A UI change and core usability get `medium`, not `high`, so that `high` still means "first". A forge with a priority field of its own (Linear, Jira, GitHub's **Priority** issue field, Bitbucket, Azure DevOps; #5747) takes it there instead of a label.
- **`on hold` means do not start (Alex, 2026-11-15).** An item labelled `on hold` (or on hold in the forge's own field) sorts below every other issue in `forge/next`, and no lead or lane picks it up next: it waits for Alex.
- **`linux-ok` marks an issue a Linux machine can do (Alex, 2026-11-15, #5810).** A lane can do all of it on Linux: Go (the daemon, the control plane), the web page, docs or tooling. The Product Owner adds it when it files the issue, only when none of these is true: it changes `App/`, `Remote/`, `Shared/`, `Host/` or `Packages/AgentsKit`; it changes `Packages/Wire` (the Swift types are written by hand and `WireSchemaTests` runs on macOS); it needs a walk on the scratch Mac app or the simulator, or Alex's Mac or devices. **Every agent that starts a lane** for a `linux-ok` issue (a lead, a standing epic's lead, the Product Owner or intake when it queues a lane, a workflow such as Fix main, a release helper; Alex, 2026-11-16, #5877) passes a Linux machine that `list_machines` shows online as `machine` to `start_session`, so the Mac's build lease stays free for the Swift lanes; with none online, or when the start fails, the lane runs on the Mac, as before. **A lead runs on any machine** (the Mac or a Linux one): it writes no code and holds no build lease, so it takes no capacity; its lanes go where their issues say, not where the lead runs.
- **The order is in the forge, not in prose.** The children are the epic's sub-issues, and a child that must wait is "blocked by" the children it waits for. A **step** is the set of children whose blockers are all closed or in an earlier step; the children of one step can run at the same time, under the open-PR limits. A "Slices" table in the epic's body is optional prose: the sub-issues and their "blocked by" links are the plan.
- **One lead per epic** (the `lead` skill, `.agents/skills/lead/`). The Product Owner files the epic and its first children; then the lead owns the plan: it starts a lane for each child whose blockers are closed, files the new children that its lanes find, and closes the epic when all its children are closed. The lead writes no code.
- **An epic gets one lead, not a place for each child.** The lead does not count as a lane; its lanes do, towards the folder's lane and open-PR limits (typically 5 to 7 at once, per project). The order of `forge/next` applies to the epic as one unit.
- **A feature is planned as up to three epics (Alex, 2026-11-24, #7037)**, each "blocked by" the one before: **design** (the data model, wireframes and mock-ups), **MVP or proof of concept** (one client, usually the Mac) and **port** (the web page and the Remote, as the tier says). This is this repo's rule only: the daemon's order does not change. The `epic-lifecycle` skill has the stages.
  - Design is in the MVP epic by default: its first children, which the build children are blocked by. The agent can ask Alex whether to make it a separate epic; that epic and its children get `priority:high`. A design issue closes on Alex's approval at its gate.
  - A proof of concept is not thrown away: it can become the MVP. One that merges follows the normal rules (gate 2, the flag, approval of a new screen).
  - The MVP epic closes when stage 8 (the performance and usability review) is done. The flag stays until the port is done. A port of one issue has no epic: it goes to #4208, blocked by the MVP epic.
  - A follow-up does not hold an epic open: one issue goes to the standing epic #4208 (a bug to #4207); several go to a new epic that is "blocked by" the first.
- **The app says "epic"** for every forge, also for Linear.

## Landing a change

- **Every change has an issue and a pull request.** Work on a branch of your own, in a worktree you moved into with move_worktree (never one made by hand with `git worktree add`, which the app never sees: #615), push it ("Verifying a lane's work"), open the PR with `gh pr create`, turn on squash auto-merge with the commit trailers (below), and wait for it to land with `wait_for_event` on `pr.merged`, `pr.closed`, `pr.blocked`, `pr.commented` and `checks.passed` (`.agents/personas/software-engineer.md`, step 7, says what to do for each); fix what CI fails. Never push to `main`.
- **Each agent's squash commit ends with its commit trailers (#6362, epic #6365).** A lane turns on auto-merge with `scripts/automerge.sh <pr> <file>`, never a bare `gh pr merge --auto --squash`: `<file>` holds the lines that the app's tool `commit_trailers` (with `pr`) gave, as they came. The script writes the squash message (each commit's message with its own trailers taken out, then one trailer block), fails on a key that is not a trailer of the rule, and turns on squash auto-merge with it. When the lane turns auto-merge on again after more work (a CI fix, a merge of `main`), it asks `commit_trailers` again and runs the script again, so `Cost`, `Tokens` and `Duration` count that work; `scripts/rearm-automerge.sh` keeps the message it finds. This repo turns `Cost` on (`.agents/policy.json`). `docs/reference/policy.md`, "Commit trailers on main", says what each trailer is. **Why:** GitHub's squash runs no hook, and this repo's squash message is `COMMIT_MESSAGES`, so a PR of several commits would give several blocks, and git reads only the last.
- **Lease `ci` before each push, not before work (Alex, 2026-11-21, #6513; was #5712, #5709).** Before each push (the first, and one that only settles a conflict), take the lease `ci` with `lease_resource`, push, and release it at once. Local work (reading, editing, building and testing on this Mac) never waits for the remote CI queue: only a push adds CI jobs. **Why:** on 2026-11-21 the line before work cost 55 waits and 4 h 08 min in one day, and Alex took three sessions out of it. The queue wait is the lease's job: a grant waits while the repo has a CI job queued, then goes to one holder at a time (#5709). When the branch conflicts with `main`, `git merge origin/main` (not a rebase, so no force-push), settle the conflict and push without running the tests again: CI runs them.
- **A UI enhancement waits for Alex only when it adds a screen, control or layout (Alex, 2026-10-27, #2811; scope 2026-11-04, #3474).** An `enhancement` PR that changes what a client shows (`App/Sources`, `Remote/Sources`, `Shared/UI`, `Web/src`) merges only after Alex approves it **when it adds one of these:**
  - **a new screen:** a window, sheet, pane, page, popover, tab, or a Settings section;
  - **a new control:** a button, menu item, toggle, field, picker, swipe or other gesture, or a keyboard shortcut;
  - **a new layout:** it moves, regroups or removes sections or controls of an existing screen, or changes how a person gets to a screen (navigation).

  **Every other UI enhancement auto-merges at once,** as a bug fix does: copy, colour, spacing, fonts, icons, the state or look of an existing control, empty states, and polish. Its body still has `## Screenshots` (one per state and per client, step 1), so Alex can look later and comment. A bug fix, and an enhancement that changes no client (daemon, wire, tooling, docs), never wait.
  - **The lane decides, and writes one line in the PR body:** `Approval: needed (new control: …)` or `Approval: not needed (no new screen, control or layout)`. When the lane is not sure, it asks for approval: a wrong "not needed" costs Alex one comment and one follow-up PR.
  - **When Alex comments on a merged PR that did not wait,** a lane changes it or reverts it, on a new PR.
  - **Why:** agents' walks find out whether a change works, not whether it is right for a person; 102 of the 296 bugs filed from 2026-10-20 to 10-27 came from the usability check, after the change had merged. But from 2026-10-28 to 11-04, 94 of 372 merged PRs waited for Alex and 74 of them (79%) were approved on the first comment: small polish went through the same gate as whole features (#3474).

  A PR that waits goes through these steps (one that does not wait does step 1, then turns on auto-merge at once):
  1. Walk the change with the run-app skill (Mac and web on a scratch app, the Remote on the walk simulator) and take **screenshots, one per state and per client**, not a video. For motion (a scroll, a gesture, an animation), add a short silent clip beside them, an animated WebP from `scripts/video/clip.sh` (#4094); a sound gets a clip with sound (#4856). Use only scratch data: the repo is public. The run-app skill's "Screenshots for Alex" says how, and `pr-shots.sh` uploads them (`<client>-<state>.png`, or `.webp` for a clip) to the PR's body with `gh pr edit --attach` (#6963): no branch, no push and no `ci` lease. GitHub refuses the bot's App token there, so that script, and nothing else, uses Alex's own `gh` login (Alex, 2026-11-23); the PR stays the bot's. The old branch `screenshots` stays for the links of old PRs; nothing pushes to it.
  2. Open the PR with **auto-merge off** and the screenshots in its body under `## Screenshots`, and **request Alex's review**: `gh pr edit <n> --add-reviewer alexec`. The requested review is the sign that the PR waits for Alex (epic #5802); the PR gets no label. Alex's list is https://github.com/pulls/review-requested.
  3. **Fix nothing else until Alex answers:** no CI fixes, rebases or conflict fixes, because they use tokens on a change Alex may not want. Wait with `wait_for_event` on `pr.reviewed`, `pr.commented` and `pr.closed`, `where: {"pr": <n>}` (#2838, #3860), and end the turn: a waiting lane holds no running place.
  4. **There is one way to approve: Alex's own review with Approve** (Alex, 2026-11-15, epic #5802), on github.com or with **Approve** in the app (the Work page or Needs you), which makes the same review. `pr.reviewed` or `pr.commented` wakes the lane with the review or the comment itself (author, state, url, body), with no need to re-read the PR. **Approve** (`pr.reviewed` by Alex, state `approved`): go on to step 5. Nothing else approves: not a comment, a message in chat, a label or an agent. When Alex says "approved" anywhere else, the lane asks Alex, on the PR, to approve it with a review. **Change it** (a review with Request changes, or any comment or review that does not approve): the lane makes the changes, takes a new set of screenshots (`pr-shots.sh` replaces the old ones), says on the PR what it changed, requests Alex's review again (`gh pr edit <n> --add-reviewer alexec`) and waits again. When the lane cannot tell what Alex wants changed, it asks on the PR and waits again. **Drop it:** `pr.closed` wakes the lane; it cleans up and ends. No step sets a label.
  5. After Alex's Approve: write `Alex approved (<review link>)` in the PR body, fix the failing checks, merge `origin/main` in (not a rebase), turn on auto-merge and land it as usual.
  - **Who an agent posts as (#3860).** Until this Mac has the agents' bot (#3858), an agent's `gh` and git post as `alexec`, so a comment an agent writes starts with `<!-- agent -->`: a comment without it is Alex's. Once the bot is installed on `alexec/Agents`, they post as `alexec-agents[bot]` (#3926): `gh pr view <n> --json author` says `app/alexec-agents`. A post as the bot needs no marker, because `pr.commented` leaves out a bot's. When a lane is not sure which it posts as, it adds the marker: it does no harm. A PR posted as `alexec` cannot be approved, because GitHub does not let `alexec` review its own PR (the app shows no Approve for it): a lane opens a PR that waits for Alex as the bot.
  - **GitHub's own rule holds the bot's PR for Alex (#3860).** `main`'s ruleset has *Require approval of changes not attributed to a person* (`require_extra_approval_for_unattributed_changes`): a PR whose changes an agent's bot made merges only after a person approves it with a review. It replaces the `agent-bots` check, removed because it did the same. A PR posted as `alexec` is not held by it, and cannot get Alex's review.
  - **A multi-PR enhancement is a stack (#1777).** It waits once, on its top PR, when any PR in it adds a screen, control or layout: Alex approves once, with screenshots of the whole feature; the stack then lands from the bottom.
  - **Voice mode** is always Alex's test, on the installed Mac app: a scratch app has no microphone or speech. Say so in the PR body.
  - **No approval labels (Alex, 2026-11-15, epic #5802; replaces the labels of 2026-10-27).** The forge's own state is the state: a requested review from Alex means the PR waits, and Alex's Approve review means it is approved. A lane adds no `needs-approval`, `approved` or `changes-wanted` label; old PRs keep theirs. There is no `.github/CODEOWNERS` (#6045): GitHub requests a code owner's review on every PR that touches the owner's paths, also one that does not wait.
- **A change to an integration's state updates its row (#1283).** A PR that adds, removes, walks, tests on a real account, breaks or fixes a third-party integration updates its row in `docs/reference/integrations.md` in the same branch, as a parity line does for `parity.md`. The runtime check (Tuesday and Friday, and in each release; #3715) writes the runtime rows; edit the others by hand. An issue about an integration gets the `integration` label.
- **Agents test every integration on real accounts (Alex, 2026-11-15, #5679; replaces #1782 and #1838).** The app tests each integration itself, of the integration and of the user experience. A lane makes each outside account it needs with the `sign-up` skill: the email agentloops@fastmail.com (codes by the `email` server), Alex's home address as the billing address (from the card secret; never written in the repo, an issue or a PR), and a Privacy.com card (`PRIVACY_CARD` or `PRIVACY_CARD_2`, by `fill_secret`; its spend limit bounds the cost). It needs no form for that account or for a charge on that card. Each test on a real account records an integration video as evidence (#1793). An integration test gets no `alex-todo` and no checklist for Alex. Only a step that no agent can do (an SMS code to Alex's phone, a passkey, root MFA) goes to Alex, by `hand_to_person` for that one step, with an issue under #3905. A lane does not wait for that step: it lands its code, and the epic's lead starts the real-account test again when the step is done. A release does not wait for a test on a real account.
- **A new App Store entitlement updates the release secrets (#2781).** A PR that adds an entitlement to an App Store target makes its profile again and updates the `release` environment's `PROFILE_…` secret in the same change (`scripts/release-secrets.sh --store`, with Alex's approval), and says so in the PR. The `testflight` job's `check-store-profiles.py` fails on a stale profile, naming the entitlement and the secret.
- **Request Alex's review only when the PR waits for Alex's approval (Alex, 2026-11-17, #6045).** A PR that waits ("A UI enhancement waits for Alex", above) requests Alex's review; no other PR does: not a bug fix, a CI, release, deploy or sign-in change, or a UI change that does not wait. When GitHub or a tool adds Alex as a reviewer to a PR that does not wait, remove the request (`gh pr edit <n> --remove-reviewer alexec`). **Why:** a requested review puts the PR on Alex's list and in the app's Needs you as waiting for Alex; the code-owner requests of #4590 (`.github/CODEOWNERS`, now removed) put PRs there that landed without a review.
- **Every issue gets its own agent, worktree and pull request (#2504).** No path is locked to one lane (Alex, 2026-11-10; it replaces the areas of #873): two lanes may change the same files, and the one that lands second rebases. A follow-up to a running lane's work waits until that lane's PR has auto-merge on, then a new agent starts on it; the parts of one spec, or a change and its per-client follow-ups, go one after another, each by its own agent. A running lane is never messaged to take another issue: a message to a lane is for its own PR (stuck, in conflict, failing checks), never to widen its work. A stack (#1777) is still one agent per PR. Land a change across many files (a rename, a removal) when no other lane is active.
- **An issue is taken** when a session is labelled `#<n>`, an open PR fixes it, or the session that filed it is not archived yet (it may be fixing it). Take the next one.
- **Re-arm auto-merge after a base change (#1741).** GitHub can leave a CLEAN, green PR with auto-merge on unmerged when its base moved (a stack landing, a retarget to main). After you change a PR's base, or turn auto-merge on just after its base moved, run `scripts/rearm-automerge.sh <pr>`. A lane or lead waiting on PRs to land runs `scripts/rearm-automerge.sh --stalled` each time it wakes: it re-arms, once per head, any PR that has been CLEAN with auto-merge on for 10 minutes, and says so on the PR. Wait on the `github` server's `checks.passed` event (#3035) alongside the others a lane already waits on, so this wakes as soon as a PR's checks go green rather than only at the next timer wake.
- **A stacked PR gets auto-merge only once its base is main (#1777).** A stacked PR's base is another lane branch. That base has no required checks, so `gh pr merge --auto` merges the PR into it at once (#1776, 2026-10-20). When the PR below lands, run `git rebase --onto origin/main <old base>`, set the base to main, then turn on auto-merge. If GitHub then leaves a clean PR unmerged, run `scripts/rearm-automerge.sh <pr>` (#1741).
- **Conflicting PRs land one at a time.** When more than one open PR is in conflict, one landing lane merges `origin/main` into each and lands them in turn, and the others' auto-merge is off until it is theirs.
- **Label your session as you go** with set_session_labels: `#<n>` for the issue, `P#<n>` for the PR, and `merged` once it lands.
